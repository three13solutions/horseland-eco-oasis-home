# Meal catalogue guest pricing: review and release boundary

## Additive admin change

- `20261120223001_meal_catalog_guest_pricing.sql` is additive and does not update catalogue prices, meal plans, EP anchors, booking/payment records or quote functions. It creates private, revisioned guest-price storage; no existing items are backfilled.
- `get_meal_guest_prices()` returns JSON `{revision, guest_policy_revision, prices}`, where `prices` is keyed by exact Services → Meals UUID and then guest key, with INR numeric values. Adult uses the existing reviewed shared-price workflow and is never written by the new RPC. Enabled paid non-adult guest types receive explicit numeric prices. A blank is not free; numeric zero is explicit. A globally free band always displays zero as derived policy, rather than a writable price. This distinction also prevents a changed age band from silently allowing paid settings.
- `save_meal_guest_prices(p_meal_id, p_prices, p_expected_revision, p_expected_guest_policy_revision)` accepts a complete map of editable keys, with omitted editable keys clearing their prices. Administrative edits are date-effective from the current Asia/Kolkata date and stored as append-only revisions. Both optimistic revisions are required. Authentication alone is insufficient: existing application admin authorization is checked; private tables are inaccessible to client roles. Existing staged-vs-live adult prices remain distinct.
- Meal-plan preview rolls up exact selected UUIDs, not titles or diet names. Add the groups (AND) and count one amount within each group (OR). The group is only deterministic when all named active choices have the same amount for that guest type. Missing, inactive, duplicate or ambiguous options must be resolved before that guest type can be quoted from catalogue rates. Choosing a priced default is a possible future feature, not implemented. Each guest's dietary selection is out of scope.

## One-time buffet setup (50%) and adults-only meals

- Review and save an exact JSON object from the **intended environment** with every Services → Meals UUID, Adult price and active state: `SELECT jsonb_object_agg(id,jsonb_build_object('adult',price,'active',is_active)) FROM public.meals;`. Include all 15 rows and preserve their active states. Pass the 12 reviewed buffet UUIDs separately from the 3 inactive Candle Light Dinner by Poolside UUIDs. For the buffets only, Child (4–9) = 50% of Adult, rounded half up to two decimals in INR, and Under 4 (0–3) remains free through the guest policy. Candlelight is adults-only: neither Child nor Under 4 may select it, and an absent amount never means free. Buffet/Adults-only identification uses exact reviewed UUIDs, never display names or amounts. No catalogue Adult price, plan/rate setting, quote function, flag or existing quote revision is changed.
- First apply both additive migrations in staging. `20261120223428_meal_catalog_adult_only.sql` adds a private eligibility rule and optional `adult_only_meal_ids` snapshot metadata, without assigning prices or changing checkout. The separate operator script `scripts/install-meal-catalogue-child-50-seed.sql` installs only a private database-owner function and a v2 receipt table. It retires the earlier blanket operator function without deleting any historical receipts. Never add it to automatic migrations or call it from the browser. Use the verified DB owner/authorized migration operator, not a simulated end-user JWT or a public API role. The audit receipt records the actual database session role; version entries use the reserved zero UUID to distinguish the service operation from an individual admin edit.
- To rehearse, start a transaction, capture current catalogue revision from `meal_catalog_pricing_private.state` and guest policy revision from `public.get_guest_age_policy()`, then call `SELECT meal_catalog_pricing_private.seed_buffet_child_50_percent(<reviewed_catalogue_rev>, <reviewed_guest_policy_rev>, '<reviewed_uuid_to_adult_active_json>'::jsonb, <reviewed_buffet_uuid_array>, <reviewed_adults_only_uuid_array>);`. Use a previously reviewed snapshot, not a subquery taken within the invocation. Confirm the returned row counts and amounts, then **ROLLBACK** during rehearsal. Commit a later production run only as a separately authorized operator step on the verified target. The seed aborts all writes if any ID, Adult price, active flag, revision or expected band differs. A committed retry with identical inputs returns the stored receipt without overwriting later admin changes.
- This is a draft catalogue setup, not a checkout release. Existing booking prices and price snapshots remain unchanged: the quote integration is separately staged and defaults OFF; an existing released catalogue revision stays pinned.

## Local validation

Install the pinned test dependency only in a local test checkout (not app runtime dependencies):

```sh
npm install --no-save --ignore-scripts --no-package-lock @electric-sql/pglite@0.3.10
node scripts/test-meal-catalogue-db.mjs
```

The local harness runs an in-memory PostgreSQL fixture: initial empty state, anon/non-admin denial, admin RPC grant, private-table denial, stale revision failures, guest key validation and paise precision, explicit zero vs unset, adult prices untouched, append-only revisions, dated lookup, AND/OR arithmetic and inactive choice refusal. It also exercises the owner-only buffet seed, ID/price/revision drift rollback, odd-paise rounding, zero, explicit adults-only eligibility, historical correction rather than deletion, and idempotence after a later edit.

The optional regression harness accepts a **trusted read-only** keyed-engine definition from a representative Supabase staging baseline:

```sh
node scripts/test-meal-catalogue-db.mjs --quote-fixture /absolute/path/to/keyed-engine-baseline.sql
```

Obtain the baseline as a single function definition from the trusted database's `pg_get_functiondef('public.calculate_keyed_rate_variants_engine(uuid,date,date,uuid,integer,integer,integer,text,jsonb)'::regprocedure)`, without writing remotely or copying auth tokens. The harness replaces unrelated room, policy and availability data with fixtures and exercises the existing keyed-engine pricing loop itself. It checks gate-off deep equality/fingerprints, draft-vs-released revision isolation, per-guest maths, unchanged EP source price and accommodation, cancellation adjustment, free buffet infant versus ineligible adults-only child/infant, one nightly record per verified / known-preserved EP night, adult unchanged on opaque legacy, conservative family behavior on opaque and mixed nights, and differing OR choices. Fixture tests do **not** establish full Supabase staging, browser checkout, manual bookings or production readiness.

## Engine integration candidate; do not enable in production

`scripts/stage-meal-catalogue-quote-engine.sql` is **not** a migration to deploy automatically. It is an isolated-staging candidate with two independent gates: the existing keyed-guest release and a new private catalogue gate pinned to an effective date, a reviewed catalogue revision, the reviewed guest-policy revision and exact reviewed plan-group membership. The server never consumes a newer draft prices revision while quoting, and a subsequent group/rule change that makes the pinned snapshot inapplicable requires re-review. The private gate is OFF by default. The script aborts if the expected keyed-engine source points drift. It changes only the **target meal** charge where the source room and meal split is known. It does not replace historical adult supplement versions or change the AP-to-EP source deduction where explicitly preserved. Full-preservation pricing remains historically pinned. For newly calculated meal plans linked to an adults-only meal, both Child and Under 4 are ineligible once the rule is part of the released catalogue revision; before that, no draft rule can change booking quotes. Dietary-choice capture and standalone live add-on selection are not added by this patch. For a family on opaque legacy dates not covered by full preservation, the candidate keeps RO while declining paid plans rather than assigning guessed meal splits. This UX and policy choice need sign-off before release.

The gate is not publicly writable and has not been enabled. This work does not migrate live quote, checkout or manual booking onto catalogue rates. In particular, today's Edge routing can accept old fresh numeric-only requests and fall back to the legacy v2 engine; before using the catalogue release flag, guard fresh public/manual requests so they re-quote with the current keyed contract. Preserve snapshot-based resume/finalize for existing payment intents. The STAGING script exposes a service-role-only read RPC, `get_meal_catalogue_checkout_gate()`, returning the conservative gate state even if other pins are invalid. Deploy the database function first with the gate OFF, then verify the Edge preflight can read it before deploying Edge; never enable until both callers are confirmed. Do not treat an old-client bypass as success just because a new-preview quote is correct.

Staging acceptance must check ordinary approved EP rates, preserved festive dates, December 23–25 mixed known split, and the March 31–April 2 transition / April 1 opaque packages. Compare actual website and manual quotes and payment-order preparation with no production bookings/payments. Verify Adult, Child and Under-4 meal charges, availability and fallback messaging, cancellation/discount interactions, effective dates, exact group IDs, date-local correctness, mixed-night totals, stale quotes and old-client rejection. Rate rollout and any Lovable publish must be separately coordinated; existing rates, saved intents and policies must remain unchanged until then.
